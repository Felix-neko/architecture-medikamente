# Задание 6. Классификация данных

## Архитектура решения

### Входные данные

Движок получает данные из двух источников:

1. **CDC-события из Kafka** — изменения в транзакционных БД (CRM DB, Med Record DB)
2. **Схема данных из OpenMetadata** — информация о тегах полей (`pii`, `extra_protected`, `dlp_needed`)

**Проблема:** Структуры данных на входе **подвержены изменениям** и **не размечены** на предмет класса конфиденциальности.

### Решение: многослойная классификация

#### 1. Schema Discovery Service

Отвечает за **автоматическое обнаружение новых полей**:
- Сравнивает текущую схему CDC-события с известной схемой в OpenMetadata
- При обнаружении нового поля — помечает его как `unclassified`
- Отправляет уведомление дата-инженеру для ручной разметки

#### 2. ML Classifier Service

Автоматическая классификация полей с использованием ML:
- **Named Entity Recognition (NER)** — обнаружение ФИО, адресов, телефонов в текстовых полях
- **Pattern Matching** — regex для email, ИНН, СНИЛС, паспорта
- **Контекстный анализ** — определение медицинских данных по ключевым словам

Выходные классы:
| Класс | Описание | Пример |
|-------|----------|--------|
| `pii_direct` | Прямо идентифицирующие данные | ФИО, паспорт, телефон |
| `pii_indirect` | Косвенно идентифицирующие | Адрес, дата рождения |
| `medical` | Медицинские данные | Диагноз, назначения |
| `financial` | Финансовые данные | Сумма платежа |
| `public` | Публичные данные | Код МКБ-10 |

#### 3. Tokenization Service

Токенизация идентифицирующих полей:
- **ФИО, email, телефон** → SHA-256 хеш с salt
- **Паспорт, СНИЛС, ИНН** → формат-сохраняющее шифрование (FPE)
- **Адреса** → обобщение до региона
- **Даты** → сдвиг на случайное число дней (±30)

#### 4. DLP Integration Service

Интеграция с InfoWatch Traffic Monitor для **финальной проверки**:
- Отправляет токенизированные данные на проверку
- Если DLP обнаруживает ПДн — данные не загружаются в `dlp_approved`
- Логирует все случаи срабатывания DLP для анализа ошибок токенизации

## Слои данных в ClickHouse

В соответствии с принципами Privacy by Design организуем **несколько слоёв** в аналитическом хранилище:

```
┌─────────────────────────────────────────────────────────────────┐
│                        ClickHouse                               │
├─────────────────────────────────────────────────────────────────┤
│  raw_sources (схема)                                            │
│  ├── Полные данные с ПДн                                        │
│  ├── Теги: pii, pii_direct, pii_indirect, medical               │
│  └── Доступ: только admin, pii_read                             │
├─────────────────────────────────────────────────────────────────┤
│  tokenized_sources (схема)                                      │
│  ├── Токенизированные данные (ФИО → хеш, телефон → хеш)         │
│  ├── Теги: pii_hidden для токенизированных полей                │
│  └── Доступ: admin, pii_read, analyst                           │
├─────────────────────────────────────────────────────────────────┤
│  dlp_approved_sources (схема)                                   │
│  ├── Данные после проверки DLP (гарантированно без ПДн)         │
│  ├── Теги: dlp_approved                                         │
│  └── Доступ: analyst, external_analyst (временные роли)         │
└─────────────────────────────────────────────────────────────────┘
```

### Дополнительные меры защиты

1. **Row-Level Security (RLS)** — ограничение доступа к строкам по роли
2. **Column-Level Security** — скрытие колонок с тегом `pii` для аналитиков
3. **Query Audit Log** — логирование всех запросов в ElasticSearch
4. **Data Masking Views** — представления с автоматическим маскированием

## Метрики эффективности классификации

### 1. Качество ML-классификатора

| Метрика | Описание | Целевое значение |
|---------|----------|------------------|
| **Precision** | Доля истинно позитивных среди предсказанных | ≥ 95% |
| **Recall** | Доля обнаруженных ПДн среди всех ПДн | ≥ 99% |
| **F1-score** | Гармоническое среднее Precision и Recall | ≥ 97% |

*Recall важнее Precision* — лучше ложно заблокировать, чем пропустить ПДн.

### 2. Метрики DLP-интеграции

| Метрика | Описание | Целевое значение |
|---------|----------|------------------|
| **DLP False Positive Rate** | Доля ложных срабатываний DLP | < 5% |
| **DLP Escape Rate** | Доля ПДн, прошедших DLP | 0% |
| **Tokenization Coverage** | % полей с тегом `pii`, которые токенизированы | 100% |

### 3. Операционные метрики

| Метрика | Описание | Целевое значение |
|---------|----------|------------------|
| **Processing Latency** | Время от CDC-события до загрузки в ClickHouse | < 5 мин |
| **Unclassified Fields** | Количество полей без классификации | 0 (после 24ч) |
| **Schema Drift Events** | Количество обнаруженных изменений схемы | мониторинг |

### Как метрики помогают в оптимизации

1. **Низкий Recall** → дообучение ML-модели на пропущенных примерах
2. **Высокий DLP False Positive** → улучшение токенизации, анализ паттернов
3. **Высокий Processing Latency** → масштабирование Spark-кластера
4. **Schema Drift Events** → триггер для ручной разметки новых полей

## Масштабируемость (Scalability)

### Текущая архитектура

- **Apache Airflow** — оркестрация DAG (1 воркер)
- **Classification Engine** — Python/PySpark (1 нода)
- **Kafka** — 3 брокера, партиционирование по `table_name`

### При увеличении объёма данных

| Нагрузка | Решение |
|----------|---------|
| **10x записей** | Горизонтальное масштабирование Spark (добавление воркеров) |
| **Новые источники** | Добавление Debezium-коннекторов, новые топики Kafka |
| **Сложные схемы** | Выделение Schema Registry (Confluent) для версионирования |
| **Больше ML** | GPU-ноды для NER-моделей, батчинг запросов к DLP |

### При увеличении количества пользователей

| Нагрузка | Решение |
|----------|---------|
| **Больше аналитиков** | Масштабирование ClickHouse (шардирование по дате) |
| **Внешние аналитики** | Отдельный ClickHouse-реплика только для `dlp_approved` |
| **Audit нагрузка** | Отдельный ElasticSearch-кластер для аудита |

### Архитектурные паттерны для масштабирования

1. **Event Sourcing** — все изменения через Kafka, возможность replay
2. **CQRS** — отделение write (CDC → Kafka) от read (ClickHouse)
3. **Saga Pattern** — откат при ошибке DLP (данные не попадают в `dlp_approved`)

## Заключение

Classification Engine обеспечивает:

1. **Privacy by Design** — данные классифицируются и токенизируются до попадания в аналитику
2. **Автоматизация** — ML-классификация новых полей без ручного вмешательства
3. **Верификация** — интеграция с DLP для гарантии отсутствия ПДн
4. **Прослеживаемость** — полный аудит всех операций с данными
5. **Масштабируемость** — архитектура на базе Kafka/Spark/Airflow
