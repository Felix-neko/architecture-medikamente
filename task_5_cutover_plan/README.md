# Задание 5. Разработка cutover-плана

## Выбор стратегии миграции

### Выбранный подход: Parallel Run

Из трёх вариантов миграции (High-Level Design, Parallel Run, Branch by Abstraction) выбираем **Parallel Run** — параллельный запуск старой и новой системы с постепенным переводом нагрузки.

**Суть подхода:** какое-то время сотрудники вносят данные и в Excel-файлы на сетевой ФС, и в новую CRM-систему. Источником истины остаются файлы на сетевой папке, но главврач контролирует, чтобы все данные были внесены и в CRM.

### Почему Parallel Run?

| Преимущество | Описание |
|--------------|----------|
| **Низкий риск** | При ошибках в новой системе — старая продолжает работать |
| **Постепенное обучение** | Сотрудники осваивают систему параллельно с работой |
| **Валидация данных** | Можно сравнивать данные в двух системах |
| **Плавный переход** | Нет «большого взрыва» — переключаемся по готовности |

### Почему не Branch by Abstraction?

**Branch by Abstraction** предполагает создание абстрактного интерфейса между системами и постепенный перенос функциональности. В нашем случае это **не подходит**:

- Нужен интерфейс между **человеком и системой**, а не между программными компонентами
- Невозможно переключить всех сотрудников на новый интерфейс одномоментно
- «Старый казацкий способ» (Excel) будет жить минимум месяц

### Почему не High-Level Design?

**High-Level Design** не противоречит Parallel Run, но:
- По условию задачи мы проектируем **часть систем**, а не целиковый продукт
- Не проектируем: онлайн-платежи, программную интеграцию с лабораториями/страховыми и многие другие системы.

## Этапы миграции

**Важно:** команда разработки очень маленькая (1 DevOps + 1 фронтэнд + 1 бэкэнд), поэтому параллельная разработка бывает затруднена.

Но: часто задач нужно делать заранее, даже если MVP задержится (чтобы потом нормально разрабатывать этап 2, не переписывая MVP полностью).

### Что нужно разработать (последовательно)

Для полноценной системы нужны следующие сервисы (см. [task_2/README.md](../task_2_design/README.md)):

| Сервис | Описание | Оценка |
|--------|----------|--------|
| **CRM API** | Паспортные данные, записи, расписание | 6-8 недель |
| **Веб-интерфейс CRM** | Регистрация, поиск, запись на приём | 4-6 недель |
| **Auth Proxy** | Авторизация, проверка ИС, rate limiting | 3-4 недели |
| **Consent Manager API** | Информированные согласия | 3-4 недели |
| **Med Record API** | Медкарты, протоколы, диагнозы | 6-8 недель |
| **Веб-интерфейс МК** | Ведение медкарт врачами | 4-6 недель |
| **Classification Engine** | Обезличивание данных для аналитики | 4-6 недель |

**Итого:** ~30-42 недели разработки = **7-10 месяцев**

### Этап 1. Миграция CRM (Parallel Run, месяц 5-6)

**Принцип Parallel Run:** все сотрудники работают **одновременно** и в Excel, и в CRM. Источник истины — Excel до тех пор, пока подавляющее большинство не освоит обе системы.

| № | Действие | Ключевые задачи | Ответственные | Срок | Риски и меры |
|---|----------|-----------------|---------------|------|--------------|
| 1.1 | **Миграция данных пациентов** | Импорт из Excel в PostgreSQL (CRM DB) | Бизнес-аналитик, DevOps | День 1 (выходные) | Риск: потеря данных. Мера: бэкап Excel, сверка количества |
| 1.2 | **Миграция журналов записей** | Импорт истории записей в CRM DB | Бизнес-аналитик | День 1-2 | Риск: битые связи. Мера: валидация по UUID |
| 1.3 | **Запуск Parallel Run** | **Все** сотрудники вносят данные и в Excel, и в CRM. Источник истины — Excel | Главврач, IT-директор | День 2 | Риск: двойная работа. Мера: упростить формы CRM |
| 1.4 | **Мониторинг и исправление багов** | Сбор обратной связи, оперативное исправление | Фронтэнд, Бэкэнд | Неделя 1-2 | Риск: много багов. Мера: дежурство разработчиков |
| 1.5 | **Еженедельная валидация** | Сравнение CRM и Excel: количество записей, суммы, расхождения | Бизнес-аналитик | Неделя 1-3 | Риск: расхождения. Мера: разбор каждого случая |
| 1.6 | **Контроль заполнения CRM** | Главврач проверяет, что **все** сотрудники вносят данные в CRM | Главврач | Неделя 2-3 | Риск: сопротивление. Мера: личный контроль |
| 1.7 | **Переключение источника истины** | Когда >90% данных вносится в CRM — CRM становится основной системой | IT-директор, Главврач | Неделя 4 | Риск: не все освоили. Мера: дополнительное обучение отстающих |

**Критерии перехода к Этапу 1.5:**
- Подавляющее большинство сотрудников (>90%) вносят данные в CRM
- Расхождение данных CRM/Excel < 1%
- Нет критических багов более 2 недель

## План отката

В случае критических проблем — **возврат к Excel/папкам** в течение 2 часов:

| Триггер | Действие | Ответственный |
|---------|----------|---------------|
| Недоступность CRM > 2 часов | Переключение на Excel, уведомление сотрудников | IT-директор |
| Потеря данных в CRM | Восстановление из бэкапа PostgreSQL + откат к Excel | DevOps |
| Критические баги (невозможно работать) | Откат деплоя, возврат к Excel | DevOps, IT-директор |

**После отката:**
1. Анализ причин сбоя
2. Исправление проблемы на тестовом стенде
3. Повторная миграция по согласованию с главврачом

## Заключение

Выбранная стратегия **Parallel Run** позволяет:
- Минимизировать риски потери данных и простоя
- Постепенно обучать персонал
- Валидировать данные в реальном времени
- Иметь план отката на каждом этапе

**Особенности плана для маленькой команды:**
- Разработка идёт **последовательно** (невозможно параллелить)
- Сначала CRM (регистратура), потом медкарты (врачи)
- Общий срок: **~12 месяцев** вместо 10 недель при большой команде

Ключевые факторы успеха:
1. **Найм специалистов** до начала разработки (DevOps, фронтэнд)
2. **Аудит и очистка данных** — без этого миграция обречена
3. **Итеративная разработка** — MVP → обратная связь → доработка
4. **Личный контроль главврача** — мотивация персонала
