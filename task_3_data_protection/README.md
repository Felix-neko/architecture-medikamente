# Задание 3. Оценка Data Encryption at Rest and In Transit

Документ содержит стратегию защиты данных для целевой архитектуры (TO-BE) компании «Медикаменте».

---

## 1. Классификация данных

### 1.1. Классы данных по чувствительности

| Класс | Описание | Примеры данных | Профиль риска |
|-------|----------|----------------|---------------|
| **C1: Критический** | Особая категория ПДн (ст. 10 152-ФЗ), медицинская тайна | Диагнозы, результаты анализов, ВИЧ-статус, психиатрические данные | Штраф до 18 млн ₽, уголовная ответственность, потеря лицензии |
| **C2: Высокий** | Идентифицирующие ПДн | ФИО, паспортные данные, дата рождения, адрес, телефон, email | Штраф до 10 млн ₽, репутационный ущерб |
| **C3: Средний** | Косвенно идентифицирующие данные | Номер полиса ДМС, ID пациента в связке с датой визита | Штраф до 5 млн ₽ |
| **C4: Низкий** | Операционные данные без ПДн | Расписание специалистов, прайс-лист услуг, справочники | Минимальный риск |
| **C5: Служебный** | Технические данные | Логи без ПДн, метрики, конфигурации | Риск при компрометации инфраструктуры |

### 1.2. Классификация по состоянию данных

| Состояние | Описание | Компоненты TO-BE |
|-----------|----------|------------------|
| **At Rest** | Данные в хранилищах | PostgreSQL, Redis, MinIO, ClickHouse, ElasticSearch, 1С БД |
| **In Transit** | Данные при передаче | HTTPS между сервисами, gRPC, Kafka, JDBC/S3 connections |
| **In Use** | Данные в оперативной памяти | Сервисы API, Auth Proxy, ETL-процессы |

## 2. Данные для защиты и инструменты защиты

### 2.1. Основная таблица защиты данных

| Данные | Класс | В чём необходимость защиты | Инструменты защиты At Rest | Инструменты защиты In Transit |
|--------|-------|---------------------------|---------------------------|-------------------------------|
| **Диагнозы, анамнез, назначения** | C1 | Медицинская тайна (ст. 13 323-ФЗ), особая категория ПДн | AES-256 на уровне полей в PostgreSQL (pgcrypto), отдельная схема `med_records`, ключи в Vault | mTLS между сервисами, TLS 1.3 для клиентов |
| **Результаты анализов** | C1 | Медицинская тайна, передача партнёру-лаборатории | AES-256 шифрование файлов в MinIO (SSE-S3), ключи в Vault | TLS 1.3 + подпись запросов HMAC при интеграции с лабораторией |
| **ВИЧ-статус, психиатрические данные** | C1 | Повышенная защита по 323-ФЗ | AES-256 с отдельным ключом, доступ только лечащему врачу | mTLS + дополнительная проверка ИС в Auth Proxy |
| **ФИО пациента** | C2 | Идентификация субъекта ПДн | AES-256 в отдельной таблице `patient_identity`, ограничение на выборку (≤50 записей) | TLS 1.3 |
| **Паспортные данные** | C2 | Документ, удостоверяющий личность | AES-256 в таблице `patient_documents`, доступ только receptionist | TLS 1.3, не передаются во внешние системы |
| **Телефон, email** | C2 | Контактные данные для идентификации | AES-256 в таблице `patient_contacts` | TLS 1.3 |
| **Дата рождения** | C2 | В связке с ФИО — полная идентификация | AES-256 совместно с ФИО | TLS 1.3 |
| **Номер полиса ДМС** | C3 | Связь с внешней страховой | AES-256 в `patient_insurance` | TLS 1.3 при передаче на Insurance Portal |
| **Информированное согласие (ИС)** | C3 | Юридически значимый документ | Подпись HMAC, хранение в PostgreSQL | TLS 1.3 |
| **JWT-токены, сессии** | C5 | Компрометация = доступ к данным | FERNET-шифрование в Redis, TTL, ротация ключей | TLS 1.3, Secure + HttpOnly cookies |
| **Ключи шифрования, пароли БД** | C5 | Компрометация = доступ ко всем данным | HashiCorp Vault (Shamir's Secret Sharing), auto-unseal | mTLS к Vault API |
| **Логи API-запросов** | C4/C5 | Могут содержать ПДн в URL/headers | Маскирование ПДн перед записью в ElasticSearch | TLS 1.3 к ElasticSearch |
| **CDC-события Kafka** | C1-C3 | Реплика данных из PostgreSQL | Шифрование топиков (Kafka SSL), retention policy | TLS между Debezium и Kafka, SASL_SSL |
| **Аналитические данные ClickHouse** | C1-C4 | Агрегированные медицинские данные | Слои данных: `raw_sources` (зашифровано), `dlp_approved` (обезличено) | TLS 1.3 |
| **Документы МК (сканы, снимки)** | C1 | Могут содержать ФИО на изображении | MinIO SSE-S3 (AES-256), DLP-сканирование, теги в OpenMetadata | TLS 1.3, pre-signed URLs с TTL |
| **Данные 1С (платежи, зарплата)** | C2-C3 | Финансовые и кадровые ПДн | TDE на уровне PostgreSQL (1С в клиент-серверном режиме) | TLS между 1С клиентом и сервером |

### 2.2. Матрица доступа к классам данных (RBAC + ABAC)

| Роль | C1 (Критический) | C2 (Высокий) | C3 (Средний) | C4 (Низкий) |
|------|------------------|--------------|--------------|-------------|
| **patient** | Только свои данные | Только свои данные | Только свои данные | ✓ |
| **receptionist** | ✗ | ✓ (ограниченно) | ✓ | ✓ |
| **nurse** | ✓ (при наличии ИС) | ✓ | ✓ | ✓ |
| **doctor** | ✓ (при наличии ИС) | ✓ | ✓ | ✓ |
| **analyst** | Только `dlp_approved` | ✗ | Обезличенные | ✓ |
| **admin** | ✓ (аудит) | ✓ | ✓ | ✓ |

## 3. Средства автоматизированного контроля

### 3.1. Контроль доступа

| Средство | Назначение | Контролируемые данные |
|----------|------------|----------------------|
| **Auth Proxy** | Централизованная проверка JWT, ролей и ИС | Все запросы к CRM API, Med Record API, MinIO |
| **Keycloak** | Аутентификация, User Federation с AD | Учётные записи, роли, сессии |
| **Consent Manager API** | Проверка информированного согласия | Доступ к медкартам (C1) |
| **PostgreSQL Row-Level Security** | Ограничение на уровне строк | Данные пациентов в таблицах |
| **MinIO Bucket Policies** | Ограничение доступа к папкам `/patient_uuid/` | Документы МК |

### 3.2. Контроль утечек (DLP)

| Средство | Назначение | Точка контроля |
|----------|------------|----------------|
| **OpenMetadata + теги** | Классификация полей БД и файлов | PostgreSQL, ClickHouse, MinIO |
| **DLP-сканер (ETL)** | Обнаружение ПДн в неструктурированных данных | Перед записью в `dlp_approved_sources` |
| **Rate Limiting (Auth Proxy / Istio)** | Защита от массового скачивания | API endpoints |
| **Ограничение выборки (CRM API)** | ≤50 записей при поиске пациентов | `GET /patients?search=...` |

### 3.3. Аудит и мониторинг

| Средство | Назначение | Хранение |
|----------|------------|----------|
| **ElasticSearch** | Логи всех API-запросов (без тела ответа) | 90 дней, затем архив |
| **PostgreSQL audit extension** | Логирование SELECT/UPDATE/DELETE на C1-C2 данные | Отдельная БД аудита |
| **Alerting (Prometheus + Alertmanager)** | Аномалии доступа, неудачные авторизации | — |
| **SIEM-интеграция** | Корреляция событий ИБ | Внешняя SIEM (опционально) |

### 3.4. Автоматические проверки релизов

| Проверка | Инструмент | Триггер |
|----------|------------|---------|
| Соответствие тегов OpenMetadata и юнит-тестов | LLM (Claude Sonnet) | Pre-release |
| Сканирование секретов в коде | GitLeaks / TruffleHog | CI/CD pipeline |
| Проверка TLS-конфигурации | SSL Labs API / testssl.sh | Weekly scheduled |
| Тесты на несанкционированный доступ | Security unit tests | CI/CD pipeline |

## 6. Рекомендации по внедрению

### 6.1. Приоритеты внедрения

| Приоритет | Мера | Обоснование |
|-----------|------|-------------|
| **P0** | TLS 1.3 на всех внешних endpoints | Базовая защита in transit |
| **P0** | Vault для управления секретами | Централизация ключей |
| **P0** | Keycloak + Auth Proxy | Контроль доступа |
| **P1** | pgcrypto для C1-C2 данных | Защита at rest критичных данных |
| **P1** | MinIO SSE-S3 | Защита документов МК |
| **P1** | mTLS внутри кластера | Защита от lateral movement |
| **P2** | OpenMetadata + DLP-сканер | Автоматическая классификация |
| **P2** | Аудит-логирование в ElasticSearch | Расследование инцидентов |
| **P3** | SIEM-интеграция | Корреляция событий |

### 6.2. Метрики эффективности защиты

| Метрика | Целевое значение | Инструмент измерения |
|---------|------------------|---------------------|
| % данных C1-C2 с шифрованием at rest | 100% | OpenMetadata audit |
| % соединений с TLS 1.3 | 100% | Istio metrics |
| Среднее время обнаружения аномалии | < 15 мин | Alertmanager |
| % покрытия API security-тестами | > 90% | CI/CD reports |
| Ротация ключей шифрования | По расписанию | Vault audit log |
