# Проблемные зоны архитектуры с точки зрения бизнес-операций

Здесь дадим анализ проблемных зон текущей архитектуры компании «Медикаменте» с точки зрения влияния на бизнес-процессы, причём с учётом перспективного масштабирования до сети из 5-6 клиник.

---

## Список проблемных зон

| № | Проблемная зона                                             | Текущая реализация | Проблема при масштабировании | Рекомендация |
|---|-------------------------------------------------------------|--------------------|-----------------------------|--------------|
| 1 | **Хранение данных в Excel**                                 | patients.xlsx, журналы записей — всё в Excel-файлах | Коллизии при одновременном доступе из разных филиалов, потеря данных, невозможность параллельной работы 30+ администраторов | Миграция на централизованную СУБД (PostgreSQL) с веб-интерфейсом |
| 2 | **Единственный физический сервер**                          | Один сервер Windows Server 2022 в здании офиса | Single Point of Failure, нет отказоустойчивости, невозможно обслуживать филиалы | Переход на кластерную архитектуру или облако с георезервированием |
| 3 | **Локальная сетевая папка**                                 | Медкарты хранятся в сетевых папках | Филиалы не смогут получить доступ к медкартам других филиалов, задержки при работе через WAN | Централизованное хранилище документов с репликацией или S3-совместимое хранилище |
| 4 | **1С в файловом режиме**                                    | 1С:Бухгалтерия и 1С:Торговля работают с файловыми базами | Максимум 5-10 одновременных пользователей, блокировки, низкая производительность | Переход на клиент-серверный режим 1С с PostgreSQL/MS SQL |
| 5 | **Отсутствие API и интеграций**                             | Ручной ввод данных, копирование между системами | Невозможно автоматизировать процессы между филиалами, дублирование данных | Разработка API-слоя, интеграционная шина (Kafka/RabbitMQ) |
| 6 | **Нет единой системы записи**                               | Журналы записей — отдельные Excel-файлы для каждого врача | Пациент не может записаться в другой филиал, нет общего расписания | Централизованная система управления расписанием с веб/мобильным доступом |
| 7 | **Нет мобильного приложения и портала**                     | Запись только через телефон или личную явку | При 5-кратном росте клиентов регистратура станет узким местом | Разработка клиентского портала и мобильного приложения |
| 8 | **Отсутствие централизованной аутентификации для филиалов** | Локальный AD в одном офисе | Каждому филиалу нужен свой AD или VPN до центрального, сложность управления | Федеративная аутентификация (Keycloak/Azure AD) или доменный лес AD |
| 9 | **Ручная синхронизация справочников**                       | Прайс-листы, списки врачей — в отдельных файлах | Рассинхронизация данных между филиалами, разные цены на одни услуги | MDM-система (Master Data Management) для централизованного управления справочниками |
| 10 | **Нет системы отчётности для сети клиник**                  | Бизнес-аналитик строит отчёты вручную из Excel | Невозможно получить консолидированную отчётность по всем филиалам | BI-платформа (Metabase/Superset) + DWH |

## Детальный анализ проблемных зон

### 1. Хранение данных в Excel-файлах

**Текущее состояние:**
- список пациентов — единый файл на сетевой ФС со списком всех пациентов
- Журналы записей — отдельные файлы на ФС вида `/Записи/{дата}/{специалист}.xlsx`
- Медкарты — папки с файлами на сетевом диске

**Проблемы при масштабировании:**
- При 5 филиалах будет ~15 администраторов, одновременно работающих с файлами
- Excel не поддерживает параллельное редактирование с гарантией целостности
- Уже сейчас бывают коллизии при 2 администраторах
- Нет транзакционности — потеря данных при сбоях
- Нет индексов — поиск по 50 000+ записей будет критически медленным

**Рекомендации:**
```
┌─────────────────────────────────────────────────────────┐
│                    Целевая архитектура                  │
├─────────────────────────────────────────────────────────┤
│  PostgreSQL (Primary)  ←──репликация──→  PostgreSQL     │
│     (ЦОД 1)                              (Standby)      │
│         ↑                                   ↑           │
│         └──────────── pgbouncer ────────────┘           │
│                          ↑                              │
│         ┌────────────────┼────────────────┐             │
│    Филиал 1         Филиал 2          Филиал N          │
└─────────────────────────────────────────────────────────┘
```

- Миграция на PostgreSQL с репликацией
- Веб-приложение для работы с данными
- Connection pooling для оптимизации соединений

---

### 2. Единственный физический сервер

**Текущее состояние:**
- Один сервер Windows Server 2022 в здании офиса
- На нём: AD, DNS, DHCP, файловый сервер, Exchange, 1С

**Проблемы при масштабировании:**
- Single Point of Failure — отказ сервера останавливает всю компанию
- Нет географической распределённости для филиалов
- Невозможно обеспечить SLA 99.9% для медицинского учреждения
- Производительность не масштабируется вертикально бесконечно

**Рекомендации:**
- Разделение сервисов по отдельным серверам/контейнерам
- Переход на Kubernetes для stateless-сервисов
- Георезервирование: основной ЦОД + резервный
- Или миграция в облако (Yandex Cloud / VK Cloud) с мультизональностью

---

### 3. Локальная сетевая папка для медкарт

**Текущее состояние:**
- Медкарты хранятся в папках на файловом сервере Windows
- Путь: `\\server\medcards\{patient_id}\`

**Проблемы при масштабировании:**
- Филиалы не имеют прямого доступа к сетевой папке
- Работа через VPN будет медленной (большие файлы диагностики)
- Нет версионирования документов
- Нет метаданных и поиска по содержимому

**Рекомендации:**
- S3-совместимое хранилище (MinIO on-premise или Yandex Object Storage)
- CDN для ускорения доступа из филиалов
- Document Management System для медицинских документов
- Elasticsearch для полнотекстового поиска

---

### 4. 1С в файловом режиме

**Текущее состояние:**
- 1С:Бухгалтерия и 1С:Торговля в файловом режиме
- Данные в файлах `.1cd` на сетевом диске

**Проблемы при масштабировании:**
- Файловый режим поддерживает максимум 5-10 пользователей
- При большем количестве — блокировки и падение производительности
- Нет возможности работы из удалённых филиалов
- Резервное копирование — копирование файлов (не консистентное)

**Рекомендации:**
- Переход на клиент-серверный режим 1С:
  - Сервер 1С:Предприятие
  - СУБД: PostgreSQL (бесплатно) или MS SQL
- Публикация через веб-сервер для доступа из филиалов
- Или переход на 1С:Fresh (облачная версия)

---

### 5. Отсутствие API и интеграций

**Текущее состояние:**
- Данные вводятся вручную в каждую систему
- Нет автоматического обмена между Excel, 1С, порталами партнёров

**Проблемы при масштабировании:**
- Ручной ввод × 5 филиалов = 5× больше ошибок и времени
- Невозможно построить сквозные бизнес-процессы
- Интеграция с внешними системами (ЕГИСЗ, лаборатории) требует API

**Рекомендации:**
```
┌──────────────────────────────────────────────────────────┐
│                   API Gateway (Kong/Nginx)               │
├──────────────────────────────────────────────────────────┤
│   Клиентский     Портал        Мобильное    Интеграции   │
│   портал         сотрудников   приложение   (лаборатории)│
├──────────────────────────────────────────────────────────┤
│                Integration Bus (Kafka/RabbitMQ)          │
├──────────────────────────────────────────────────────────┤
│  Сервис      Сервис       Сервис      Сервис     1С      │
│  пациентов   расписания   платежей    медкарт    (API)   │
└──────────────────────────────────────────────────────────┘
```

- Разработка REST/GraphQL API для всех операций
- Интеграционная шина для асинхронного обмена
- API-адаптеры для 1С и внешних систем

---

### 6. Нет единой системы записи на приём

**Текущее состояние:**
- Журналы записей — Excel-файлы для каждого врача
- Запись только через телефон или личный визит

**Проблемы при масштабировании:**
- Пациент филиала А не может записаться к специалисту филиала Б
- Нет видимости загрузки всех специалистов сети
- Невозможно оптимизировать распределение пациентов
- Нет онлайн-записи — нагрузка на регистратуру растёт линейно

**Рекомендации:**
- Централизованная система управления расписанием
- Веб-портал для онлайн-записи пациентов
- Мобильное приложение с push-уведомлениями
- Интеграция с колл-центром для телефонной записи

---

### 7. Нет клиентского портала и мобильного приложения

**Текущее состояние:**
- Взаимодействие с пациентами только офлайн или по телефону
- Результаты анализов приходят по email

**Проблемы при масштабировании:**
- При 5× росте клиентов регистратура не справится
- Конкуренты с онлайн-сервисами будут привлекательнее
- Нет возможности для self-service операций

**Рекомендации:**
- **MVP (2-3 месяца):** Веб-портал с онлайн-записью
- **Расширение (6 месяцев):** Мобильное приложение
- **Функционал:**
  - Просмотр истории посещений
  - Онлайн-запись к врачу
  - Просмотр результатов анализов
  - Оплата услуг онлайн
  - Push-напоминания о визитах

---

### 8. Отсутствие централизованной аутентификации

**Текущее состояние:**
- Локальный Active Directory в одном офисе
- Нет SSO для внешних систем

**Проблемы при масштабировании:**
- Каждому филиалу нужна своя инфраструктура AD или VPN
- Сложность управления учётными записями в нескольких доменах
- Нет единого входа для сотрудников сети

**Рекомендации:**
- **Вариант 1:** Доменный лес AD с site-to-site VPN
- **Вариант 2 (рекомендуется):** Keycloak/Azure AD B2C
  - Федеративная аутентификация
  - SSO для всех систем
  - MFA из коробки
  - OAuth2/OIDC для приложений

---

### 9. Ручная синхронизация справочников

**Текущее состояние:**
- Прайс-листы, списки врачей, услуг — в отдельных файлах
- Обновление вручную

**Проблемы при масштабировании:**
- Разные цены на одни услуги в разных филиалах
- Рассинхронизация справочников
- Ошибки при ручном обновлении

**Рекомендации:**
- Централизованное хранилище справочников (MDM)
- Версионирование изменений
- Автоматическая синхронизация во все филиалы
- Audit trail изменений

---

### 10. Нет консолидированной отчётности

**Текущее состояние:**
- Бизнес-аналитик строит отчёты вручную из Excel
- Jupyter + Python для анализа

**Проблемы при масштабировании:**
- Невозможно получить отчёт по всей сети клиник
- Ручная работа не масштабируется
- Нет real-time дашбордов для руководства

**Рекомендации:**
```
┌─────────────────────────────────────────────────────────┐
│                     BI Dashboard                        │
│               (Metabase / Apache Superset)              │
├─────────────────────────────────────────────────────────┤
│                   Data Warehouse                        │
│                    (ClickHouse)                         │
├─────────────────────────────────────────────────────────┤
│                      ETL Pipeline                       │
│                  (Airflow / dbt)                        │
├─────────────────────────────────────────────────────────┤
│   PostgreSQL    │    1С    │   Внешние источники        │
│   (операц.)     │          │                            │
└─────────────────────────────────────────────────────────┘
```

- Построение DWH на базе ClickHouse (уже в стеке техдиректора)
- BI-платформа для самообслуживания
- ETL-процессы для консолидации данных из всех филиалов

## Целевая архитектура для сети клиник

```
                                    ┌─────────────────┐
                                    │   Пациенты      │
                                    │ (Web/Mobile)    │
                                    └────────┬────────┘
                                             │
                                    ┌────────▼────────┐
                                    │   API Gateway   │
                                    │   (Kong/Nginx)  │
                                    └────────┬────────┘
                                             │
        ┌────────────────────────────────────┼────────────────────────────────────┐
        │                                    │                                    │
┌───────▼───────┐                   ┌────────▼────────┐                  ┌────────▼────────┐
│   Сервис      │                   │    Сервис       │                  │    Сервис       │
│   пациентов   │                   │   расписания    │                  │    медкарт      │
└───────┬───────┘                   └────────┬────────┘                  └────────┬────────┘
        │                                    │                                    │
        └────────────────────────────────────┼────────────────────────────────────┘
                                             │
                                    ┌────────▼────────┐
                                    │  Message Broker │
                                    │     (Kafka)     │
                                    └────────┬────────┘
                                             │
        ┌────────────────────────────────────┼────────────────────────────────────┐
        │                                    │                                    │
┌───────▼───────┐                   ┌────────▼────────┐                  ┌────────▼────────┐
│  PostgreSQL   │                   │    S3 Storage   │                  │   ClickHouse    │
│  (Primary)    │                   │    (MinIO)      │                  │     (DWH)       │
└───────────────┘                   └─────────────────┘                  └─────────────────┘

        │                                    │                                    │
        └────────────── Филиал 1 ────────────┼───────────── Филиал N ─────────────┘
                         (VPN)                               (VPN)
```

Эта архитектура обеспечивает:
- **Масштабируемость:** Горизонтальное масштабирование сервисов
- **Отказоустойчивость:** Нет единой точки отказа
- **Географическое распределение:** Филиалы работают через VPN/интернет
- **Гибкость:** Независимое развитие сервисов
