# Сопоставление процессов компании с требованиями безопасности данных

Документ содержит анализ бизнес-процессов компании «Медикаменте» в контексте:
- требований по обеспечению безопасности данных (риски утечки ПДн);
- рисков нарушения бизнес-процессов (коллизии, потеря данных).

---

## 1. Регистрация пациента

### Описание процесса
- Пациент лично приходит в регистратуру, показывает паспорт и сообщает персональные данные
- Администратор открывает файл `patients.xlsx` со списком пациентов на сетевой папке и ищет там ФИО или номер паспорта
- Администратор заполняет анкету пациента и создаёт папку медкарты на сетевой ФС
- Администратор добавляет новую запись в Excel-файл со списком пациентов

### Обрабатываемые данные
| Тип данных | Категория | Уровень конфиденциальности |
|------------|-----------|---------------------------|
| ФИО | ПДн | Высокий |
| Дата рождения | ПДн | Высокий |
| Паспортные данные | ПДн | Высокий |
| Телефон, email | ПДн | Средний |
| Адрес прописки | ПДн | Средний |
| Место работы/учёбы | ПДн | Средний |
| Хронические заболевания | Медицинские данные (особая категория ПДн) | Критический |

### Несоответствия требованиям безопасности

| Требование/практика | Статус | Описание проблемы |
|---------------------|--------|-------------------|
| **152-ФЗ: Защита ПДн** | ❌ Не выполняется | ПДн хранятся в незашифрованном Excel-файле, доступном всем сотрудникам |
| **Принцип минимизации данных** | ❌ Не выполняется | Собирается избыточная информация (место работы, адрес) без обоснования необходимости |
| **Контроль доступа (RBAC)** | ❌ Не выполняется | Любой сотрудник может открыть список пациентов и папку его медкарты |
| **Шифрование at Rest** | ❌ Не выполняется | Файлы хранятся в открытом виде |
| **Аудит доступа** | ❌ Не выполняется | Нет логирования, кто открывал/редактировал файл |
| **Целостность данных** | ⚠️ Частично | Возможны коллизии при одновременном редактировании |
| **Информированное согласие** | ✅ Выполняется | Пациент подписывает согласие |

### Риски для бизнес-процессов

| Риск | Описание |
|------|----------|
| **Коллизии при редактировании** | При одновременном сохранении `patients.xlsx` двумя администраторами — затирание изменений коллеги. Сейчас редко (2 администратора видят друг друга), при масштабировании — критично |
| **Потеря данных** | Нет транзакционности — при сбое данные могут быть потеряны |

## 2. Запись на приём

### Описание процесса
- Пациент лично приходит / звонит в регистратуру / врач пишет администратору в мессенджер
- Администратор проверяет регистрацию в `patients.xlsx` (файл в сетевой папке)
- Администратор открывает журнал записей `/Записи/{дата}/{специалист}.xlsx` и вносит ФИО пациента в свободное окно
- Журнал ведётся отдельными файлами для каждого специалиста, чтобы снизить вероятность коллизий
- При личной явке — подписывается информированное согласие (сканируется и сохраняется в МК)

### Обрабатываемые данные
| Тип данных | Категория | Уровень конфиденциальности |
|------------|-----------|---------------------------|
| ФИО пациента | ПДн | Высокий |
| Дата и время записи | Операционные | Низкий |
| Специалист | Операционные | Низкий |
| Информированное согласие | Медико-правовой документ | Высокий |

### Несоответствия требованиям безопасности

| Требование/практика | Статус | Описание проблемы |
|---------------------|--------|-------------------|
| **Защита каналов связи** | ❌ Не выполняется | Врачи передают ФИО пациентов через мессенджеры (неконтролируемый канал) |
| **DLP (предотвращение утечек)** | ❌ Не выполняется | ПДн передаются через личные устройства врачей |
| **Контроль доступа** | ❌ Не выполняется | Все администраторы видят все записи ко всем специалистам |
| **Шифрование in Transit** | ❌ Не выполняется | Передача через мессенджеры без гарантий шифрования |
| **Аудит коммуникаций** | ❌ Не выполняется | Переписка в мессенджерах не логируется корпоративно |

### Риски для бизнес-процессов

| Риск | Описание |
|------|----------|
| **Коллизии в журнале записей** | Если администратор и врач одновременно редактируют журнал — затирание данных. Отдельные файлы для каждого специалиста снижают, но не устраняют риск |
| **Потеря записей** | При сбое или коллизии — пациент приходит, а его записи нет |
| **Неудобство записи** | Нет онлайн-записи — нагрузка на регистратуру, конкуренты привлекательнее |

## 3. Оплата медицинских процедур

### Описание процесса
- Администратор ищет запись пациента в журнале записей
- Администратор печатает талон на оказание платной медицинской услуги (код записи, цена, специалист)
- Кассир вводит название услуги, код записи и цену в «1С:Бухгалтерия»
- 1С загружает данные в кассовый аппарат
- Пациент производит оплату (карта/наличные/QR)
- Кассовый аппарат проводит платёж через фискальную систему, печатает чек

### Обрабатываемые данные
| Тип данных | Категория | Уровень конфиденциальности |
|------------|-----------|---------------------------|
| ФИО пациента | ПДн | Высокий |
| Код записи | Операционные | Низкий |
| Сумма платежа | Финансовые | Средний |
| Реквизиты платежа | Финансовые (PCI DSS) | Критический |

### Несоответствия требованиям безопасности

| Требование/практика | Статус | Описание проблемы |
|---------------------|--------|-------------------|
| **PCI DSS** | ✅ Выполняется | Платёжные данные обрабатываются ККМ, считаем, что связь ККМ-1С через TCP/IP зашифрована |
| **Разделение обязанностей** | ❌ Не выполняется | Кассир самостоятельно вводит данные и подтверждает платёж |
| **Аудит финансовых операций** | ⚠️ Частично | 1С ведёт журнал, но централизованный аудит отсутствует |
| **Защита талонов** | ❌ Не выполняется | Талоны содержат ПДн и не защищены |

### Риски для бизнес-процессов

| Риск | Описание                                                                                                                                                                                                                                                                                                                |
|------|-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| **1С в файловом режиме** | Можно работать, подключаясь к сетевой ФС, но максимум 5-10 одновременных пользователей. При масштабировании — блокировки и падение производительности и простой, если пропала связь с центральным филиалом. Но: можно сравнительно легко перейти на клиент-серверный режим, поставив его на VPS в любом дата-центре ; ) |

## 4. Согласование процедуры со страховой компанией (ДМС)

### Описание процесса
- Пациент получил от врача назначение и спрашивает, покроет ли ДМС это назначение
- Администратор заходит в ЛК партнёра на портале страховой компании
- Администратор формирует заявку, вводя выписки из истории болезни и загружая файлы с результатами анализов
- Часть заявок согласуется автоматически (в течение 1 минуты), часть — вручную сотрудником страховой (в течение часа)
- Получив согласование, администратор делает пометку в журнале записей, что услуга оплачена по ДМС

### Обрабатываемые данные
| Тип данных | Категория | Уровень конфиденциальности |
|------------|-----------|---------------------------|
| ФИО пациента | ПДн | Высокий |
| История болезни | Медицинские данные | Критический |
| Результаты анализов | Медицинские данные | Критический |
| Диагнозы | Медицинские данные (особая категория) | Критический |
| Данные ДМС-полиса | Страховые | Высокий |

### Несоответствия требованиям безопасности

| Требование/практика | Статус | Описание проблемы |
|---------------------|--------|-------------------|
| **Передача данных третьим лицам** | ⚠️ Риск | Медицинские данные передаются на внешний портал страховой без контроля их дальнейшего использования |
| **Минимизация данных** | ❌ Не выполняется | Передаётся полная история болезни, хотя для согласования может быть достаточно кодов процедур |
| **Договор на обработку ПДн** | ❓ Неизвестно | Не описаны договорные обязательства страховой по защите данных |
| **Аудит передачи** | ❌ Не выполняется | Нет логирования, какие именно данные были переданы |
| **Шифрование** | ⚠️ Частично | HTTPS на портале, но загружаемые файлы не шифруются дополнительно |
| **Право на забвение** | ❌ Не выполняется | Нет механизма отзыва данных у страховой |

### Риски для бизнес-процессов

| Риск | Описание |
|------|----------|
| **Коллизия в журнале записей** | Администратор делает пометку об оплате ДМС в том же файле, который редактируют другие — риск затирания |

## 5. Приём у врача / медицинские процедуры

### Описание процесса
- Пациент приходит к врачу
- Врач открывает файл с журналом записи, находит запись пациента и помечает, что приём состоялся
- Врач открывает папку медицинской карты пациента на сетевой ФС и добавляет новый файл (описание симптомов, диагноз, лист назначений)
- Туда же добавляются файлы с результатами инструментальной диагностики (рентген, УЗИ, ЭКГ)
- Если нужны рецептурные препараты — врач выписывает их на бумажном бланке

### Обрабатываемые данные
| Тип данных | Категория | Уровень конфиденциальности |
|------------|-----------|---------------------------|
| Жалобы, симптомы | Медицинские данные | Критический |
| Диагноз | Медицинские данные (особая категория) | Критический |
| Назначения | Медицинские данные | Высокий |
| Результаты диагностики | Медицинские данные | Критический |
| Рецепты | Медицинские данные | Высокий |

### Несоответствия требованиям безопасности

| Требование/практика | Статус | Описание проблемы |
|---------------------|--------|-------------------|
| **Врачебная тайна** | ❌ Нарушается | Любой сотрудник может открыть медкарту любого пациента |
| **Контроль доступа** | ❌ Не выполняется | Нет ограничения «только лечащий врач» |
| **Целостность медзаписей** | ❌ Не выполняется | Файлы можно редактировать/удалять без следа |
| **Версионирование** | ❌ Не выполняется | Нет истории изменений медицинских записей |
| **Аудит доступа** | ❌ Не выполняется | Невозможно узнать, кто читал медкарту |
| **Шифрование** | ❌ Не выполняется | Диагнозы хранятся в открытом виде |
| **Защита особых категорий ПДн** | ❌ Не выполняется | Нет дополнительной защиты для чувствительных диагнозов |

### Риски для бизнес-процессов

| Риск | Описание |
|------|----------|
| **Коллизия в журнале записей** | Врач отмечает приём в том же файле, который может редактировать администратор — риск затирания |
| **Потеря медицинских записей** | Нет версионирования файлов в медкарте — при сбое или ошибке данные теряются без возможности восстановления |

## 6. Сдача лабораторных анализов

### Описание процесса
- Пациент заходит в процедурную к медсестре с направлением на сдачу анализов
- Медсестра открывает файлы медицинской карты на сетевой ФС: общую информацию о пациенте и направление на анализы
- Медсестра заходит в ЛК лаборатории-партнёра через веб-интерфейс и создаёт заявку (часть данных из файла с информацией о пациенте)
- Заявка **НЕ анонимная** — требования прослеживаемости образцов
- Веб-интерфейс лаборатории генерирует штрих-код, медсестра печатает и наклеивает на пробирки
- Результаты анализов лаборатория присылает пациенту и клинике **по email**

### Обрабатываемые данные
| Тип данных | Категория | Уровень конфиденциальности |
|------------|-----------|---------------------------|
| ФИО пациента | ПДн | Высокий |
| Дата рождения | ПДн | Высокий |
| Контактные данные | ПДн | Средний |
| Виды анализов | Медицинские данные | Высокий |
| Результаты анализов | Медицинские данные | Критический |

### Несоответствия требованиям безопасности

| Требование/практика | Статус | Описание проблемы |
|---------------------|--------|-------------------|
| **Передача данных третьим лицам** | ⚠️ Риск | ПДн и медданные передаются в систему лаборатории-партнёра |
| **Защита email-канала** | ❌ Не выполняется | Результаты анализов отправляются по обычному email без шифрования |
| **Договор на обработку ПДн** | ❓ Неизвестно | Не описаны обязательства лаборатории по защите данных |
| **Право на доступ** | ⚠️ Частично | Пациент получает результаты, но не имеет доступа к ЛК |
| **Аудит передачи** | ❌ Не выполняется | Нет логирования передаваемых данных |
| **Минимизация данных** | ⚠️ Частично | Передаётся больше данных, чем минимально необходимо |

### Риски для бизнес-процессов

| Риск | Описание |
|------|----------|
| **Зависимость от email** | Результаты анализов приходят по email — ненадёжный канал, письма могут теряться или попадать в спам |

## 7. Внутренняя аналитическая работа

### Описание процесса
- Главврач формирует запрос на подготовку отчёта (устно или по email)
- Бизнес-аналитик самостоятельно открывает журналы записей на файловом сервере и собирает данные о приёмах
- Бизнес-аналитик открывает папки медицинских карт и выгружает данные: диагнозы, назначения, результаты анализов
- Бизнес-аналитик заходит в 1С Бухгалтерия и выгружает данные о платежах
- Бизнес-аналитик вручную сводит все данные в Excel-файл, формируя отчёт
- Готовый отчёт передаётся главврачу по email или на флешке

### Обрабатываемые данные
| Тип данных | Категория | Уровень конфиденциальности |
|------------|-----------|---------------------------|
| ФИО пациентов | ПДн | Высокий |
| Даты приёмов | Операционные | Низкий |
| Диагнозы | Медицинские данные (особая категория) | Критический |
| Назначения | Медицинские данные | Высокий |
| Результаты анализов | Медицинские данные | Критический |
| Суммы платежей | Финансовые | Средний |
| Выручка по услугам | Финансовые | Средний |

### Несоответствия требованиям безопасности

| Требование/практика | Статус | Описание проблемы |
|---------------------|--------|-------------------|
| **Принцип минимальных привилегий** | ❌ Не выполняется | Бизнес-аналитик имеет доступ ко ВСЕМ медкартам, журналам и данным 1С |
| **152-ФЗ: Защита ПДн** | ❌ Не выполняется | ПДн копируются на локальный ПК без контроля |
| **Контроль доступа (RBAC)** | ❌ Не выполняется | Нет ограничения доступа к данным, не относящимся к аналитике |
| **Аудит доступа** | ❌ Не выполняется | Невозможно узнать, какие данные выгружал бизнес-аналитик |
| **Шифрование at Rest** | ❌ Не выполняется | Отчёты с ПДн хранятся на локальном ПК в открытом виде |
| **Обезличивание данных** | ❌ Не выполняется | Данные для аналитики не анонимизируются |
| **DLP** | ❌ Не выполняется | Отчёты с ПДн передаются на флешках и по email без контроля |

### Риски для бизнес-процессов

| Риск | Описание |
|------|----------|
| **Избыточный доступ** | Для формирования отчёта бизнес-аналитик получает доступ к данным, которые ему не нужны (например, конкретные диагнозы) |
| **Утечка через флешки** | Отчёты с ПДн передаются на съёмных носителях — риск потери/кражи |
| **Нет версионирования отчётов** | Невозможно отследить, какая версия отчёта была передана |

## 8. Передача аналитических данных вовне

### Описание процесса
- Внешний аналитик (материнская компания / консультант) запрашивает данные для анализа
- Бизнес-аналитик клиники самостоятельно собирает данные из журналов записей, медицинских карт и 1С Бухгалтерия
- Бизнес-аналитик формирует выгрузку в Excel-файл, содержащий полные ПДн пациентов
- Бизнес-аналитик отправляет файл внешнему получателю: по email или через облачный диск (Яндекс.Диск, Google Drive) с публичной ссылкой

### Обрабатываемые данные
| Тип данных | Категория | Уровень конфиденциальности |
|------------|-----------|---------------------------|
| ФИО пациентов | ПДн | Высокий |
| Диагнозы | Медицинские данные (особая категория) | Критический |
| Результаты анализов | Медицинские данные | Критический |
| Назначения | Медицинские данные | Высокий |
| Суммы платежей | Финансовые | Средний |

### Несоответствия требованиям безопасности

| Требование/практика | Статус | Описание проблемы |

## Ключевые требования безопасности и их реализация

### 152-ФЗ «О персональных данных»
- **Требование:** Обеспечить конфиденциальность ПДн, ограничить доступ, получить согласие
- **Текущее состояние:** Согласие получается, но защита данных отсутствует

### Privacy by Design
- **Требование:** Встраивать защиту данных на этапе проектирования
- **Текущее состояние:** Система развивалась без учёта требований ИБ

### Data Minimization
- **Требование:** Собирать только необходимые данные
- **Текущее состояние:** Собирается избыточная информация в анкетах

### Encryption at Rest / In Transit
- **Требование:** Шифровать данные при хранении и передаче
- **Текущее состояние:** Шифрование не применяется

### Access Control (RBAC/ABAC)
- **Требование:** Разграничить доступ по ролям
- **Текущее состояние:** Все сотрудники имеют доступ ко всем данным

### Audit Trail / Data Lineage
- **Требование:** Вести журнал доступа и операций с данными
- **Текущее состояние:** Аудит не ведётся

### DLP (Data Loss Prevention)
- **Требование:** Предотвращать утечки конфиденциальных данных
- **Текущее состояние:** DLP не реализован, данные можно свободно копировать

## Выводы

Анализ показывает, что **ни один из восьми рассмотренных бизнес-процессов компании не соответствует** в полной мере требованиям по обеспечению безопасности конфиденциальных данных.

### Проблемы с точки зрения ИБ:

1. **Архитектурный долг:** Система строилась без учёта требований ИБ
2. **Отсутствие разграничения доступа:** Нарушен принцип Least Privilege — любой сотрудник видит все данные
3. **Незащищённые каналы:** Мессенджеры, email без шифрования
4. **Нет контроля над данными у партнёров:** Страховая, лаборатория получают полные данные
5. **Невозможность аудита:** Нельзя расследовать инциденты
6. **Передача данных без обезличивания:** Бизнес-аналитик имеет полный доступ ко всем данным и передаёт их вовне без анонимизации

### Проблемы с точки зрения бизнес-процессов:

1. **Коллизии при редактировании Excel:** Уже сейчас бывают при 2 администраторах — при масштабировании станут критичными
2. **Потеря данных:** Нет транзакционности, версионирования — сбои ведут к потере информации
3. **Single Point of Failure:** Единственный сервер без резервирования
4. **1С в файловом режиме:** Не выдержит масштабирования

Для устранения выявленных несоответствий требуется комплексная модернизация ИТ-инфраструктуры с применением принципов **Privacy by Design** при проектировании целевой архитектуры.
